## Design decisions

### ADR-001: Time sync via Wi-Fi (NTP/SNTP), radio off in normal use

**Context**: TOTP requires an accurate clock (typical tolerance ±30 s). The X4 Pro has no battery-backed RTC, and the device is air-gapped by design (rule 5). Manual timestamp entry (tested in Phase 4) introduces an offset of several seconds and is error-prone.

**Decision**: Time synchronization via SNTP over Wi-Fi, **only during provisioning or on the user's explicit request**. Outside of sync sessions, the Wi-Fi radio is disabled (`esp_wifi_deinit` + netif destroyed, or equivalent).

**Justification**:
- Daily use remains air-gapped; the radio is an attack surface that only exists for a few seconds per sync.
- NTP carries no secret: the worst-case scenario (hostile/spoofed NTP server) shifts the time → codes become temporarily invalid (DoS), but no key can be extracted nor any code forged. Tolerated by the threat model.
- RTC drift between syncs (~1 s/day) remains well within the validity window.

**Alternatives discarded**:
- Manual time entry: imprecise (copy-paste offset), validated as a fallback solution only.
- GPS module: extra hardware, cost, bulk.
- Permanent Wi-Fi: violates rule 5 and multiplies the attack surface.

**Open questions** (to be settled in Phase 6/7):
- ~~Store Wi-Fi credentials for a quick resync, or ask for them again on every sync?~~ **Settled**: never stored — entered at each sync session, forgotten afterward. No auto-connect; the radio is off outside of sync sessions.
- ~~Resync frequency~~: on user action only (RTC drift countdown displayed to inform them).
- ~~Fallback without a network?~~ **Settled**: manual entry always available, via **a UI with a human-readable time/date (HH:MM + date), not a Unix timestamp**. UX details in Phase 6 (`UI-SPECS.md`): HH:MM + date entry, with a sync-on-minute-boundary trick (the user confirms when their reference clock reaches :00 → ~1 s accuracy); the conversion to UTC epoch and timezone handling are internal.

### ADR-002: Encrypted database (application-level blob), not an encrypted partition

**Context**: F-04 requires encrypted storage with a key derived from the PIN. Two options: encrypted partition (eFuse hardware flash encryption, or a software block layer) vs. an application-level encrypted database.

**Decision**: **Encrypted application-level blob** in a raw partition: AES-256-GCM (mbedtls), key = PBKDF2-HMAC-SHA256(PIN, salt). The entire blob is encrypted/decrypted in RAM on every mutation. No filesystem.

**Justification**:
- Hardware flash encryption has a fixed per-device key (eFuse): it doesn't depend on the PIN → incompatible with the "PIN-locked" model. Furthermore, eFuse/secure boot state on the X4 Pro Developer Edition is unknown — a dependency to avoid.
- A software-encrypted block layer amounts to reimplementing a filesystem + wear-leveling: disproportionate effort.
- Data format: a few KB → the entire blob fits in RAM, no edge case. Changing the PIN = re-encrypting the blob.

**Possible post-v1.0 hardening**: add hardware flash encryption as a complementary layer (cold-boot protection while powered off), without replacing the PIN layer.

### ADR-003: Update via SD or serial only; no secure boot before the final prerelease; no ATECC608A

**Context**: the external design doc (§8, §10) proposed network OTA
(`esp_https_ota`), Secure Boot v2 + Flash Encryption "planned" from the start,
and an optional ATECC608A (I2C) secure element.

**Decision** (user-validated 2026-09-13):
1. **Firmware update: SD or serial (UART) only — never over the
   network.** Wi-Fi OTA is excluded from scope (alpha → v1.0).
2. **Secure Boot v2 / Flash Encryption: not in alpha, not in beta — only
   conceivable for the final prerelease** (eFuse is irreversible, would break
   the UART flashing workflow during dev; the application-level encrypted blob
   already covers data-at-rest protection).
3. **No ATECC608A planned** — no secure element; the offline barrier
   remains the slow KDF (see ADR-004).

**Justification**: the v1 threat model assumes an attacker without
prolonged physical access; the PIN protects the data, not the firmware. The
network attack surface is null by construction (no listener, no network
update).

### ADR-004 (proposed): KDF = Argon2id instead of PBKDF2-HMAC-SHA256

**Context**: PBKDF2-HMAC-SHA256 parallelizes very well on GPU/ASIC
(SHA256 is not memory-hard): the space of a 6-digit PIN (~10⁶) falls in
~1-2 days on a consumer GPU with "250 ms" iterations. The external design doc
recommends Argon2id, feasible thanks to the 8 MB of PSRAM.

**Proposed decision**: key = `Argon2id(PIN, salt, m=8 MB, t=4, p=1)`
(parameters to be calibrated for ~0.5-1 s/attempt on the S3), via a port of
libsodium/monocypher. INTERFACES.md §1.1 updated accordingly.

**Status**: ✅ VALIDATED 2026-09-13 (replaces PBKDF2 in INTERFACES.md §1.1
and FEATURES.md F-04).

### ADR-005 (proposed): SD export with a dedicated passphrase + versioned format

**Context**: F-06b exports the blob with the same PIN key → a stolen SD card
alone (compromise without the device) is useless, but a stolen SD + device =
everything lost. The external design doc proposes a separate export
passphrase and a structured file format.

**Proposed decision**:
- File `/x4pro-export-v1.bin`: `magic(8B) | version(2B) | timestamp(8B) |
  entry_count(4B) | salt(16B) | nonce(12B) | Argon2id(export_passphrase) →
  AES-256-GCM(internal plaintext) | tag(16B)`.
- Atomic write (temp + rename), never overwritten
  (`export-YYYY-MM-DD.enc`).
- Import: parse + verify tag **before** touching the current keystore,
  bounded sizes. Distinct from the firmware update (ADR-003).
- The "PIN mode" backup (same key as the device) remains possible but is
  not the default.

**Status**: ✅ VALIDATED 2026-09-13 (INTERFACES.md §3 and FEATURES.md F-06b
updated accordingly).

### ADR-006 (proposed): Time sync via a "trusted terminal", hierarchy BLE → serial → Wi-Fi

**Context**: ADR-001 fixes manual Wi-Fi SNTP sync. The external design doc
(§4.3, §5, §6) proposes turning the phone into a *trusted terminal*:
a replaceable time beacon, never a data peer.

**Proposed decision**:
1. **The trusted terminal is trusted only for the time.** No sensitive
   data ever travels over any radio/serial channel — never encrypted, never
   in plaintext. The keystore only moves via SD (ADR-005).
2. **Three channels, all manually triggered** (never automatic sync):
   - **BLE CTS** (service 0x1805 / char 0x2A2B): the X4 Pro is a GATT
     *client* (NimBLE), scan → connect → read → disconnect, ~3-5 s, no
     pairing. Accuracy ~1 s, sufficient for 30 s TOTP windows.
   - **Serial/USB**: the PC sends the time over the serial port (mechanism
     already validated in the probe, `st` command). Exact accuracy, zero
     infrastructure.
   - **Wi-Fi SNTP** (ADR-001): fallback when no terminal is available.
3. **Early Phase 8 validation**: end-to-end BLE CTS test using
   nRF Connect's Advertiser to emit the CTS service — no companion app
   to write to validate. The question "does Android natively expose CTS"
   is settled by this test; otherwise a minimal companion app in v2.

**Justification**: reduces the exposure surface (no network credentials
in the nominal path), TOTP-compatible accuracy, consistent with the
air-gapped model. RTC drift (±20 ppm ≈ 1.7 s/day) requires a sync every
30-45 days; the UI displays the age of the last sync and alerts at 45 days.

**Status**: awaiting user validation.

### ADR-007: Recovery factory partition + bootloader hook (ported from an earlier reference design)

**Context**: with the dual-slot esp_ota alone, a device whose both slots are
corrupted requires a PC + cable to reflash. The user has a proven bootloader
hook (an earlier ESP32 project, same author): on button press at boot,
`bootloader_after_init` backs up otadata (free offset 0xB000, magic
0xAA55AA55), erases it and resets → the standard bootloader boots the
`factory` partition. Identical logical trigger from the app
(`esp_ota_set_boot_partition(factory)`).

**Decision (validated 2026-09-13)**:
1. Partition table updated (INTERFACES.md §2): added `factory` 1 MB,
   `CONFIG_PARTITION_TABLE_OFFSET=0xC000`, otadata backup @0xB000.
2. The current recovery path remains dual-slot (in-app update to the
   inactive slot + rollback); the factory is the **PC-less fallback**
   (flash from SD or serial).
3. The factory app reuses that earlier design's logic (SD → `esp_ota_write`, restore
   otadata); its UI is ported to the UC8279 e-ink driver (plain, text-based).
4. **Port to be validated on IDF 5.5.5** (the original code runs on 5.4.3):
   exact name of the hooks config, S3 `esp_rom_spiflash_*` signatures,
   non-strapping trigger GPIO (avoid GPIO0/3/45/46), S3 bootloader size.

**Technical documentation**: `FACTORY.md` (detailed port from the earlier
reference design, differences table, otadata mechanism, 5.5.5 validation
points).

### ADR-008: Board-agnostic skeleton, real `x4pro` board + `m5paper_mono` stub

**Context**: the project first targets the Xteink X4 Pro (already in hand,
full bring-up in Phase 5), but the M5Stack M5PaperMono (ESP32-S3R8,
native SSD1677 480x800 portrait e-paper, FT6336G touch) is a likely future
board port (out of stock at the time of the decision). Both converge
toward a 480x800 portrait UI.

**Decision (validated 2026-09-13)**:
1. The `src/` skeleton is board-agnostic: the board is selected via
   `-DMSF_BOARD=x4pro` (default), which includes `boards/${MSF_BOARD}/board_config.cmake`.
   Pattern inspired by an earlier project's board layout, simplified (no variant matrix).
2. `boards/x4pro/`: real configuration, validated on hardware (pins,
   UC8279/GT911/BM8563/CW2017 drivers, e-ink rotated 90° CW mode 0).
3. `boards/m5paper_mono/`: **documentation-only stub** (README specs) —
   no code before the hardware is in hand. The `x4pro-probe` already
   contains an SSD1677 driver path (busy=HIGH) that will serve as a base.
4. Whatever is board-specific (pins, screen/touch init, battery) lives
   under `boards/<name>/`; the application code (TOTP, store, UI) stays
   independent of the board behind the `board_config.h` interface.

**Status**: ✅ VALIDATED 2026-09-13.

### ADR-009: On/Off = deep sleep + wake-up GPIO, the device lives "off" between uses

> 📋 **Full post-mortem of the 2026-09-16 session** (7 distinct bugs,
> timeline, lessons learned): `docs/postmortem-power-factory-2026-09-16.md`.
> The amendments below remain the detailed technical reference;
> the post-mortem tells the story of the sequence and the *why*.

**Context**: the X4 Pro's Power button (GPIO3, active-LOW) is a simple
GPIO input — it does not cut power. A dedicated mechanism is therefore
needed to provide the expected on/off function while minimizing
consumption (the battery is ~2300 mAh and the target use case is a
keyfob left off most of the time).

**Proposed decision**:
1. **Software sleep** (`power_mgr_shutdown()`): `eink_power_off()`
   (the image stays displayed — e-ink is bistable), frontlight off, optional
   rails cut (touch GPIO2 HIGH, SD GPIO5 HIGH, RTC hold), then
   `esp_deep_sleep_start()` with **wake-up on GPIO3 LOW**
   (`esp_deep_sleep_enable_gpio_wakeup`). GPIO3 is an RTC GPIO (0-21):
   wake-up valid in deep sleep, RTC pull-up held during sleep.
2. **Wake-up**: Power press → S3 reboot → `esp_sleep_get_wakeup_cause()`
   → GPIO wake-up ⇒ direct jump to the UNLOCK screen (no splash).
   TOTP time survives via the BM8563 RTC (battery-backed).
3. **Architectural consequence**: the device is *almost always off*
   between uses, like the original e-reader. TOTP codes are computed
   **on demand at wake-up** — no background task, no tick.
   The 30 s progress bar only runs while the screen is on.
4. **Measurement to plan (task 8c)**: actual deep-sleep consumption with
   rails held via `rtc_gpio_hold_en` — validates (or not) the strategy of
   cutting GPIO1/2/5 rails during sleep.
5. **Factory**: unchanged for now (Power there remains the fallback select;
   sleep mode there is optional, the bistable screen keeps the menu
   displayed without consuming power).

**Alternatives discarded**:
- Light sleep: higher consumption, no benefit here (nothing runs in the
  background by design).
- Hardware power latch: doesn't exist on this board (no PMIC).

**Button semantics (validated in discussion 2026-09-13, amended 2026-09-13)**:

| State | Gesture | Effect |
|---|---|---|
| Off (deep sleep) | **Short Power press** (Right released) | Wake-up → app, UNLOCK screen |
| Off | **Power + Right held** | Wake-up → **factory** (combo detection: GPIO7 LOW within the first ms of boot) |
| Off | Right alone | Nothing — Right is not a wake source |
| Off | Right (GPIO7) held at **USB** boot (cold boot) | Factory via bootloader hook (dev/reflash case) |
| Factory active | Long Power | Back to deep sleep (restored otadata points to app0 → next short wake = app) |
| App active | Long Power | Deep sleep |

**Combo mechanism**: the wake source is Power (GPIO3) only;
at boot, the bootloader hook (`hooks.c`) samples GPIO7 ~125 ms after
boot start (100 ms pull-up stabilization + debounce) — held LOW =
deliberate combo, non-strapping so safe at reset.
**Symmetry**: Right is the recovery button everywhere — alone at USB boot
(bootloader hook), in combo with Power from deep sleep.

**Confirmation threshold (amended 2026-09-16)**: once Right is detected
pressed, it must be held continuously for **3 s** for the switch to
factory to trigger — automatically once the threshold is crossed, with no
need to release at a precise moment. Released before 3 s = cancelled,
normal boot. *Fixes a UX bug*: the previous version instead required
**releasing** Right within 5 s of its detection, on pain of cancellation
("held too long") — but nothing during boot lets the user know when this
window starts, making a precise release impossible to time in real use.
The new mechanism (hold until the threshold, no release window to guess)
is more robust and reuses the pattern already used for the app's Power
long-press (`MSF_POWER_LONG_MS`, `main.c`).

**Documented hardware constraints**:
- **Left+Power IMPOSSIBLE**: GPIO0 is a strapping pin — held LOW at
  reset (waking from deep sleep = full reset), the S3 boots into UART
  download mode. Hence the combo on Right (GPIO7 = RTC_GPIO7, non-strapping).
- Deep sleep wake-up only accepts RTC GPIOs (0-21): Power (GPIO3) is the
  only button that can wake the device alone; Right (RTC_GPIO7) can be
  part of a combo but alone does not wake it (outside the wake mask).
- **Validation point 8c**: GPIO3 LOW at reset changes the "JTAG source"
  strapping — verify that the USB console remains usable after a
  button wake-up (applies to any wake-up, combo or simple).

**Power press feedback (pattern to reuse in 8c, validated in factory 2026-09-15)**:
no buzzer (ADR-007) nor audio feedback — on e-ink, the user doesn't know
when a press has been "registered" and can release, especially with
gestures that depend on a duration (short/long/combo). Solution applied in
the factory: as soon as the raw GPIO Power press is detected (even before
debounce), trigger a splash refresh — the fact that the screen **starts**
flashing serves as a "you can release, it's registered" signal, without
waiting for the refresh to finish
(`boards/x4pro/factory/main/main.c`, main loop). This pattern will need to
be reused for app gestures (short=wake/cancel, long=deep sleep,
Power+Right=factory combo), with an additional signal to consider at the
long-press threshold crossing (distinguishing "release for short" from
"continue for long").

**Amendment 2026-09-16 — dropping the Right combo, switching to Power-only (duration)**:

The Power+Right combo described above (earlier sections of this ADR) is
**dropped**, replaced by a duration measurement on Power alone:

| Starting state | Gesture | Effect |
|---|---|---|
| App awake | Power held **< 10 s** then released | Deep sleep (existing behavior, unchanged) |
| App awake | Power held **≥ 10 s** | Switch to factory — `power_mgr_switch_to_factory()` (software: back up otadata @0xB000, erase otadata, `esp_restart()`) |
| Off (deep sleep) | Power held **< 10 s** then released | Wake-up → app, UNLOCK screen (unchanged) |
| Off (deep sleep) | Power held **≥ 10 s** continuously since wake-up | Switch to factory — handled **on the bootloader hook side** (`hooks.c`), independent of the app's state (see next amendment, fix 2026-09-16) |
| Factory active | Long Power | Back to deep sleep (unchanged) |

**Root cause of the change**: isolated empirically on hardware (2026-09-16) via
two dedicated tests — Test A (Power alone, deep sleep → hold Power) reliably
wakes the device; Test B (Power+Right held together from the start,
10 s, then released) **NEVER wakes** the device, no log, no
reaction, regardless of the hold duration. The combo prevents the hardware
wake-up itself from triggering — upstream of any bootloader hook or
software timing, hence unfixable on the firmware side without changing the
gesture.

**Consequences**:
- `hooks.c`: `RECOVERY_BUTTON_PIN` changes from `GPIO_NUM_7` (Right) to
  `GPIO_NUM_3` (Power); `CONFIRM_HOLD_US` changes from 3 s to **10 s**
  (aligned with the software threshold on the app side, same gesture
  regardless of the starting state).
- `power_mgr.h`/`power_mgr.c`: new `power_mgr_switch_to_factory()` function
  on the app-awake side (backup contract identical to `hooks.c`, but via
  `esp_flash_*` — app context, not bootloader ROM).
- `main.c` (`power_button_task`): single threshold replaced by two
  thresholds on the same button (1.5 s sleep / 10 s factory); every
  reference to `MSF_BTN_RIGHT_PIN`/GPIO7 removed from this path.
- The bootloader hook only has one trigger (`RECOVERY_BUTTON_PIN`):
  changing it to Power also migrates the **cold-boot USB** case
  (dev/reflash) — it now triggers by holding Power (10 s) on USB plug-in,
  instead of Right. Consistent with "one gesture, Power, regardless of
  context".
- Left+Power remains impossible (GPIO0 strapping, unchanged).

**Amendment 2026-09-16 (continued) — 2nd hardware bug: reading Power raw at
the bootloader breaks the wake-up itself**:

First attempt at implementing the above: `hooks.c` read
`RECOVERY_BUTTON_PIN` (now GPIO3) exactly as it did for Right — without
accounting for the fact that GPIO3 is *also* the EXT1 wake-up pin. Result
observed on hardware: **no wake-up nor factory switch possible at all**
from sleep ("once asleep, no wake-up and no factory").

**Root cause**: `esp_sleep_enable_ext1_wakeup()` configures GPIO3 via the
RTC_IO domain to act as a wake source; this configuration persists
through sleep and wake-up (the RTC domain stays powered). Right after an
EXT1 wake-up, at the `bootloader_after_init()` stage (well before any
application code), the pad is thus still routed through the RTC
domain — `esp_rom_gpio_pad_select_gpio()` + `gpio_ll_get_level()`
(a classic digital GPIO read, already used without issue for Right, which
is never a wake pin) no longer reflect the button's actual state. The
hook's confirmation loop ends up reading a frozen value, independent of
what the user is actually doing — hence the total absence of reaction
observed.

**1st fix (abandoned)**: fall straight back to
`RESET_REASON_CORE_DEEP_SLEEP`, moving the ≥ 10 s threshold to the app side
(`power_button_task`, `main.c`). Functionally correct but **rejected**
on user feedback (2026-09-16): *"switching to factory should be handled
on the bootloader side"* — if the app crashes or hangs before
`power_button_task` runs (or if the task itself hangs), no fallback
path exists anymore to reach the factory from sleep.
The bootloader hook must remain the source of truth, precisely because it
runs BEFORE any application code and thus stays accessible even with a
dead app.

**Fix adopted**: address the real root cause rather than work around it.
`bootloader_after_init()` now calls
`rtcio_ll_function_select(RECOVERY_BUTTON_PIN, RTCIO_LL_FUNC_DIGITAL)`
(`hal/rtc_io_ll.h`) — the low-level, register-based equivalent of
`rtc_gpio_deinit()` (driver component, not available/needed at the
bootloader stage) — which explicitly hands control back to the digital
domain on GPIO3 BEFORE any read. On the S3, the `rtcio_num` index maps
directly to the GPIO number (offset 0); on a "cold" reset where the pad
was never routed through RTC_IO, this call is a no-op with no side
effect. The hook can therefore again directly measure GPIO3's hold state
on **all** resets, including deep-sleep wake-up — the factory switch is
once more entirely driven by the bootloader, independent of the app's state.

The only exception kept: `RESET_REASON_CORE_SW` (software reset —
`esp_restart()`, triggered by `power_mgr_switch_to_factory()` on the app
side or `action_cancel()` on the factory side) short-circuits the button
read, since otadata is already correctly set by the caller in this case;
reading the button again here would only add a redundant 2nd confirmation
delay without changing the boot destination.

**Consequence on the table above**: the row "Off (deep sleep) →
Power held ≥ 10 s continuously since wake-up" is indeed handled **on the
bootloader hook side** (`hooks.c`), as initially stated — `main.c` only
handles long presses made once the app is already started and running.

**Amendment 2026-09-16 (continued) — task 8c, rails held through the RTC
domain during deep sleep**: point 4 of this ADR ("rails held via
`rtc_gpio_hold_en`") implemented in `boards/x4pro/app/splash.cpp`. The
digital domain powers down in deep sleep — a plain `gpio_set_level()` on
the touch (GPIO2) / SD (GPIO5) rails, both active-LOW, would leave the pad
floating for the whole sleep duration and could silently re-enable the
rail, defeating the point of turning it off first. `rails_hold_for_sleep()`
(called at the end of `board_sleep_screen_show()`, right after
`eink_power_off()`) latches touch=OFF, SD=OFF and periph=ON via
`rtc_gpio_*` (RTC domain, stays powered through sleep); `rails_for_splash()`
now starts with `rtc_gpio_hold_dis()` on the same three pins so the next
boot's normal `gpio_config()` can actually take effect (the hold otherwise
survives the deep-sleep reset). Build-verified only — the actual current
measurement (multimeter in series with the battery, comparing sleep
consumption with and without this hold) is still to be done on hardware,
which decides whether this strategy is kept as-is or needs to go further
(e.g. also isolating the pads with `esp_deep_sleep_disable_rom_logging()`/
`gpio_deep_sleep_hold_en()` at the SoC level, or revisiting the periph
rail).

**Amendment 2026-09-16 (continued) — 3rd bug: the bootloader's own
watchdog was preventing the 10 s threshold from ever being reached**:

After the fix above, the symptom persisted identically ("same thing, once
asleep the device does not wake up"), and holding for 12 s also did not
trigger the factory switch — a sign that the block occurs **even before**
the button question is settled.

**Root cause**: `bootloader_init()` (component `bootloader_support`,
`bootloader_init.c`) arms the RTC WDT (RWDT) with a **single
`CONFIG_BOOTLOADER_WDT_TIME_MS` = 9000 ms timeout** (action
`WDT_STAGE_ACTION_RESET_RTC`) **before** calling `bootloader_after_init()`
— i.e. before our hook runs. Our confirmation loop deliberately blocks
until `CONFIRM_HOLD_US` = **10,000 ms**, without ever feeding this
watchdog: it fires at exactly 9 s, **resetting the chip before the
threshold is reached**. This reset restarts the whole bootloader from
scratch, which rearms the same RWDT for a new 9 s max cycle — as long as
the user keeps holding the button, this cycle repeats indefinitely and the
10 s threshold is **never reachable**, regardless of the actual hold
duration. From the outside (screen never refreshed at this stage, no
app code executed yet), this silent reset loop is indistinguishable from a
total hang — explaining both the perceived absence of wake-up and the
absence of factory switch after 12 s.

**Fix**: `hooks.c` now explicitly feeds the RWDT
(`wdt_hal_feed()`, with `wdt_hal_write_protect_disable/enable()` — the same
pattern as `bootloader_support/src/flash_encryption/flash_encrypt.c` for
its own long operations at the same stage) on every iteration of the
confirmation loop (and once before, at pull-up stabilization time).
`CONFIRM_HOLD_US` can thus exceed
`CONFIG_BOOTLOADER_WDT_TIME_MS` safely, without needing to keep the two
values in sync.

**Amendment 2026-09-16 (continued) — 4th bug, a tooling bug, not a code
bug: `hooks.c` was never compiled into what was being tested**:

After THREE successive code fixes (combo, RTC_IO pad, watchdog) all
confirmed "clean build" but still reported broken on hardware in exactly
the same way, the cause turned out to be upstream of all the code:
`./msf_build.bat build` run from the repo **root** (what every check in
this session used) builds a bootloader that **does NOT contain `hooks.c`**
— ESP-IDF only detects `bootloader_components/` if it is a direct child of
the built project's `PROJECT_SOURCE_DIR`, and that folder lives under
`boards/x4pro/factory/`, not at the root. The bootloader actually flashed
(`installer/x4pro_app/bootloader_16MB.bin`) is **copied** from
`boards/x4pro/factory/build/bootloader/bootloader.bin` by the app's
postbuild step, without ever being rebuilt or checked for freshness by
that path — an `rm -rf build` + rebuild at the root therefore refreshes
nothing. In other words: each "still broken, identically" in this thread
was not a signal that the previous fixes had failed — it was `hooks.c`
from before this session's very first change that kept running on the
hardware on every test, in a loop. Corrected procedure documented in
`docs/FACTORY.md` §3.4. The 3 code bugs above each remain legitimate
fixes (confirmed by directly reading the compiled binary afterward) but
**none of them had actually been tested on hardware** at the time of this
amendment.

**Amendment 2026-09-16 (continued) — 5th bug, confirmed with real logs: stack
overflow in `power_mgr_switch_to_factory()`**:

With the bootloader properly tested (previous amendment) and application
logging finally working (`esp3d_log()` also never compiled either —
`add_compile_options()` after `project()` in the root CMakeLists, the same
trap as `MSF_BOARD_NAME` already documented just above in this same file
but not applied to this line; fixed via `idf_build_set_property`), the
logs showed: the **bootloader hook** path (Power held ≥ 10 s from
sleep) works correctly end to end (`... held Nms` →
`threshold reached` → factory). The **app-level** path (Power held ≥ 10 s
from App0 awake, `power_mgr_switch_to_factory()`) crashed
systematically, immediately after `erase backup sector @0xb000`:

```
***ERROR*** A stack overflow in task pwr_btn has been detected.
```

**Root cause**: `power_mgr_switch_to_factory()` declares
`uint8_t buf[FLASH_SECTOR_SIZE]` — a local buffer of **4096 bytes** — in
a task (`power_button_task`) created with `xTaskCreate(..., 4096, ...)`,
i.e. a total stack equal to just this buffer's size alone, not counting
`entry1`/`entry2`, the loop's other locals, nor the stack usage of the
`esp_flash_read/erase_region/write` calls themselves. Overflow guaranteed
as soon as the function is reached. This also retroactively explains the
"slightly grayed" splash observed after a 14 s test (§ above): it wasn't
e-ink ghosting, but a crash-reboot in the middle of a refresh.

**Fix**: `power_button_task`'s stack raised to 12288 bytes (generous
margin, this board has abundant PSRAM).

**Status**: ✅ VALIDATED 2026-09-13 (button semantics amended 2026-09-13,
Power feedback added 2026-09-15, **Right combo dropped and replaced by
Power-only (duration) on 2026-09-16** — 5 bugs fixed successively: the
Power+Right combo preventing wake-up, unreliable GPIO3 reads after EXT1
wake-up, bootloader watchdog too short, wrong bootloader tested
(tooling), app-level stack overflow. Both the bootloader hook path and the
app-level path (`power_mgr_switch_to_factory()`, with the stack fix)
revalidated on hardware with logs across all button-flow states, repeated
multiple times — 2026-09-16).

**Open observation — occasional unexplained freeze, not yet root-caused**:
across repeated test runs, the app-awake → factory switch
(`power_mgr_switch_to_factory()`, ≥10 s Power hold) has frozen on the splash
screen a small number of times (recurring, not a single isolated event),
with no serial log and no reboot. At least one occurrence coincided with
the USB/serial connector being physically detached at that moment, which
would explain a silent freeze (power/UART interruption mid-flash-write,
with no link left to log anything). Never reproduced on demand, and never
observed yet with the connector solidly attached and logs available end to
end. Treated as a connection/power artifact rather than a confirmed
firmware bug (a real stack overflow, the closest known candidate, always
produces an explicit `***ERROR*** stack overflow` message before its
reboot — not a silent permanent hang). **Not blocking** for this ADR's
validation, but left as an open watch item: if it recurs with a solid
connection and logs captured, it becomes a real bug to investigate (most
likely candidate: a flash erase/write to the otadata backup sector
@0xB000 interrupted mid-operation, leaving an inconsistent state).

### ADR-010: LVGL invalidated for the app — UI ported from `freeink-sdk` (FreeInkUI), native ESP-IDF

**Context**: the initial choice of LVGL 9.2.2 for the app's UI (made in
Phase 1, before any real e-ink bring-up) started from a generic
"classic embedded GUI framework" assumption, with no prior e-paper
experience on this project. Bring-up and debugging of the factory (session
2026-09-14/15 — `docs/hardware-specs.md`, `docs/FACTORY.md`) revealed that
e-paper has fundamentally different constraints from a TFT: pixel
bistability, a physical distinction between full refresh (GC, several
black/white sweeps to purge residual charges) vs. fast refresh (DU,
differential, no flash but accumulating ghosting), and management of a
1 bpp framebuffer. LVGL is display-technology-agnostic (`flush_cb` is
generically TFT-oriented): all of this work (the `s_prev` stale-after-a-DU
bug, calibrating the refresh budget before a forced GC, etc. — fixed this
session in `boards/x4pro/factory/main/eink.c`) would have had to be
reimplemented by hand **inside** a custom LVGL driver, with no gain over a
direct implementation.

**Discovery**: `freeink-sdk` (MIT, `references/freeink-sdk-main/`) already
has this work done, natively for this controller/board pair (X4 Pro,
UC8279) — listed in the SDK's `docs/display-driver-references.md`, and its
`Uc8279X4Driver` driver already correctly handles OLD-plane
resynchronization after EVERY refresh (a bug we had to fix ourselves in
our own driver). Its open-source sibling firmware (`crosspoint-reader`,
`references/crosspoint-reader-develop/`) runs in production on real X4 Pro
hardware, validating the driver and its UI layer (`FreeInkUI`) in real
use, not just in theory.

**Initial obstacle**: `freeink-sdk`/`crosspoint-reader` are built on
PlatformIO + the Arduino framework — two layers above the native
ESP-IDF used by the rest of MySafeFob (factory included). Adopting it
as-is would have duplicated the tooling (`build_mgr.py`/`flash_mgr.py`,
board-agnostic patterns) on a different framework.

**Porting study** (research agent, 2026-09-15, detailed results in the
conversation — not duplicated here): exhaustive reading of `EpdBus`,
`Uc8279X4Driver`, the GT911 portion of `InputManager`, and
`libs/ui/FreeInkUI/`. Verdict per component:
- **FreeInkUI** (~3000 lines, all UI components): **ports as-is** —
  freestanding C++17, a single Arduino-dependent line in the whole module
  (`src/FreeInkUI.cpp`, a weak symbol `getArduinoLoopTaskStackSize` gated
  by `#if defined(ARDUINO_ARCH_ESP32)`, never defined under native ESP-IDF
  — compiles as a no-op without even needing to be removed).
- **Uc8279X4Driver** (~1000 lines, the X4 Pro e-ink driver): **ports
  almost as-is** — only 2 direct Arduino lines (`millis`/
  `digitalRead`/`delay`), the rest goes through the `EpdBus` abstraction.
- **EpdBus** (~450 lines, low-level SPI/GPIO/ISR): **to be rewritten**
  in native ESP-IDF (`gpio_*`/`spi_device_*`/`esp_timer_get_time`) — this
  is the only genuine piece of mechanical translation.
- **InputManager (GT911)**: **ignored** — our `touch.c` (already
  validated on hardware, including the self-load/upload-host fallback and
  the recalibrated Home zone) already does the job; porting the SDK's
  version would have been pure duplication.
- **BoardConfig**: **X4 Pro profile extracted** (pins/calibration), not
  the SDK's monolithic 18-device file.

**Prototype validation** (`references/test_apps/freeinkui-poc/`,
2026-09-15): concrete, not just theoretical, proof — `FreeInkUI::
DisplayTarget` placed on top of our `eink.c` displays correctly (readable
text splash), and `Frame`/`InteractionBuffer` (FreeInkUI's native
interaction mechanism) driven by our already-validated
`buttons.c`/`touch.c` correctly resolves focus and confirmation (L/R
navigation, Home confirmation, circular wrap, action routed to the right
component — verified with supporting logs). No line of Arduino or
PlatformIO needed.

**Decision**:
1. **LVGL is dropped for the app.** The "LVGL 9.2.2 frozen" contract
   (`FEATURES.md` §7, `README.md` "Critical contracts") is invalidated and
   replaced by **FreeInkUI ported to native ESP-IDF**.
2. **Actual port** (task 8.4) in this order (taken from the study):
   `FreeInkUI` (nearly done) → X4 Pro `BoardConfig` profile extracted →
   `EpdBus` rewritten natively → `Uc8279X4Driver` ported → integration on
   our existing `eink.c`/`touch.c`/`buttons.c` (already proven by the POC).
3. **Amended 2026-09-15**: the factory also adopts FreeInkUI (at least
   `DisplayTarget`, to display a static splash at boot — cf.
   `docs/FACTORY.md`), but via **a frozen, independent
   copy** under `boards/x4pro/factory/components/`, never shared with the
   copy the app will vendor for itself. The duplication is a deliberate
   trade-off: it is the price for preserving ADR-007's core property
   ("the factory must stay minimal, self-contained, tested as-is" —
   `README.md` §Structure) — a change on the app side (freeink-sdk
   update, component rework) must never be able to break the factory.
   Rule: the factory copy is only updated by an explicit action tested on
   hardware, never automatically alongside the app's copy.
4. **Attribution**: `freeink-sdk` is MIT, derived from `open-x4-epaper/
   community-sdk` (MIT) — compatible license, attribution to be added in
   `NOTICE`/file headers of the copied files at the time of the actual
   integration (beyond the POC).

**Justification of the choice vs. the alternatives studied** (user table
2026-09-15): GxEPD2 (lightweight, good refresh control, but not designed
for this specific controller — from-scratch port) and LVGL (excellent for
complex generic UIs, but e-paper refresh control has to be hand-rolled and
X4 Pro support built from zero) both lose to FreeInkUI on the two criteria
that matter for MySafeFob: **native X4 Pro/UC8279 support** (already
done, already validated in production by crosspoint-reader) and
**sufficiently simple UI** (the real need: TOTP menu + password manager,
not an LVGL-style complex UI).

**Status**: ✅ VALIDATED 2026-09-15 (port to be carried out in task 8.4).

**Amendment (task 8.4 minimal slice, 2026-09-16 session)**: point 2's plan
to port `EpdBus`/`Uc8279X4Driver` from `freeink-sdk` is **dropped**.
Research into the already-working `references/test_apps/freeinkui-poc/`
proof-of-concept showed it never used those SDK files at all — it drives
`FreeInkUI::DisplayTarget` directly on top of MySafeFob's own,
already-validated `eink.c`/`touch.c`/`buttons.c`. Porting the SDK's
low-level driver would have been pure duplication with no benefit (the
2 hardware criteria that mattered — native X4 Pro/UC8279 support and a
simple UI — are already satisfied by our own drivers). Only
`eink_display_fb_fast()` (DU/ghost-budget refresh, previously
factory-only) was ported into the app's `eink.c` — needed for a
responsive nav loop, still 100% our own code.

### ADR-011: app1 removed — single app slot, factory as the safety net

**Context**: ADR-007 had set up a dual-slot esp_ota (`app0`/`app1`) to
allow automatic A/B rollback in case of a failed update, in addition to
the factory (PC-less fallback). After the factory's full bring-up (this
session) — e-ink/touch recovery validated, `SD -> app0` action already
functional to (re)flash the app from the factory — the question arose:
does the 2nd slot still bring anything?

**Analysis**:
1. **No network OTA** (ADR-003, settled): no scenario of an interrupted/
   corrupted transfer mid-flight that would justify an automatic
   rollback — SD updates are a single complete file, written in one shot.
2. **`esp_ota_end()` already validates the image's header/checksum**
   before making it bootable — a truncated or corrupted file is rejected
   at write time, not after a failed boot.
3. **The factory already knows how to reflash `app0` directly**
   (`SD -> app0`, validated this session): even a firmware that is
   "valid but logically broken" is repaired by going back through the
   factory (Power+Right combo, ADR-009), with no need for a second slot to
   automatically fall back to.

**Decision (user-validated 2026-09-15)**:
1. **`app1` removed from `partitions.csv`.** A single app slot (`app0`).
   `secrets` (F-05b, ADR-002: TOTP + passwords + recovery codes
   container) **enlarged from 0x40000 to 0x240000 (2.25 MB)** with the
   freed space — comfortable margin for the encrypted vault.
2. **F-06 (firmware update) becomes a factory feature, not an
   app one**: the `esp_ota_begin/write/end` + `set_boot_partition`
   sequence runs in the factory (already implemented), never in the
   running app — no risk of self-overwriting the active partition while
   it's executing, no need for the application-side self-check/mark-valid/
   rollback derivative documented in an earlier version of `INTERFACES.md` §3.
3. **Accepted trade-off**: no automatic rollback if the new firmware
   boots but is logically broken — manual recovery via the factory instead
   of an automatic fallback to the old slot. Acceptable: the factory is
   already the project's reference safety net, robust and tested
   independently of the app.
4. **Simplified factory menu**: `Boot app1`/`SD -> app1` removed
   (`boards/x4pro/factory/main/main.c`), no more
   `esp_partition_find_first(..., "app1")` probing.

**Documents updated accordingly**: `partitions.csv`,
`flash_params.json`, `docs/INTERFACES.md` §2/§3, `docs/FACTORY.md` §5.3/§6,
`docs/FEATURES.md` F-06 and acceptance criterion §8.4, `README.md`.

**Status**: ✅ VALIDATED 2026-09-15.

**Amendment 2026-09-15 (same day) — `SD -> factory` removed**: while
implementing the above, a second risk was identified (by the user):
the `SD -> factory` action inherited from the earlier reference design performed
`esp_partition_erase_range` + `esp_partition_write` **on the `factory`
partition while it is running from that same partition (XIP)** —
unlike `SD -> app0`, which writes an inactive partition. Any interruption
mid-flight (battery cut, bug, watchdog) between the erase and the end of
the write leaves the currently executing code itself invalid,
**with no PC-less recovery net at all** — exactly the scenario this
entire architecture is meant to avoid. Removed: `MENU_ACTION_SD_FACTORY`
and the `to_factory` branch of `action_sd_flash()` (`boards/x4pro/factory/main/
main.c`). The factory is now treated like the bootloader: updated
**only via USB/serial** (`flash_mgr.py --variant x4pro_factory`),
never self-service in the field — consistent with "tested as-is"
(ADR-007). Final factory menu: `Boot app0`, `SD -> app0`.

### ADR-012 (proposed): Auto-sleep on inactivity — activity manager

**Context**: ADR-009 only triggers deep sleep on an explicit long Power
press — nothing today puts the device back to sleep automatically if the
user simply forgets it awake (left on the READY/unlock/menu screen). Since
the X4 Pro's casing cannot be opened (confirmed 2026-09-16, previously
assumed possible for task 8c's bench measurement), the actual deep-sleep
current draw can no longer be measured or tuned on this unit by direct
instrumentation — the only lever left to control real-world battery drain
is making sure the device is **never left awake longer than necessary**,
rather than trying to shave the sleep current itself.

**Decision (spec only — implementation deferred, see below; validated
2026-09-16)**:
1. An **activity manager** tracks the last user interaction across the
   **three** available input sources — Power button, touch, and the
   serial/REPL console — and triggers the same path as a manual long
   Power press (`board_sleep_screen_show()` + `power_mgr_shutdown()`,
   frontlight already turned off as part of that sequence per ADR-009
   pt.1) once **all three** have been idle for the timeout.
2. **Idle timeout: 45 s** of no input on any of the three sources
   (button, touch, serial). Fixed default for now — the F-03
   "adjustable delay" wording still applies for a future settings screen,
   but 45 s is the validated starting value, not a placeholder.
3. **Scope carved out from task 8c**: this ADR only documents the
   decision now (project philosophy, "no code without a document"/"no
   feature without a test" — ROADMAP.md intro). The actual implementation
   needs a real activity signal loop (touch events, in particular), which
   does not exist yet in the Phase 8 skeleton (no touch driver wired into
   the app — see ADR-010, task 8.4). **Implementation deferred to task
   8.4**, alongside the FreeInkUI touch integration it depends on. Until
   then, the REPL `sleep` command and the manual Power long-press
   (ADR-009) remain the only ways to enter deep sleep.
4. **Trade-off accepted for now**: between today and task 8.4, a device
   left awake (e.g. on the READY screen) stays awake indefinitely (no
   auto sleep) — acceptable since the Phase 8 skeleton is a dev/bring-up
   build, not the shipped UX.

**Status**: ✅ VALIDATED 2026-09-16 (45 s timeout, three tracked sources:
button/touch/serial). **Implemented and hardware-validated** as part of
task 8.4's minimal slice (`boards/x4pro/app/ui_nav.cpp`, see ADR-013):
the device correctly enters deep sleep on its own after 45 s of no
button/touch/serial input, confirmed on hardware.

**Amendment 2026-09-18**: the timeout is now a runtime, NVS-persisted
value (`settings_store_get/set_idle_timeout_s()`,
`boards/x4pro/app/settings_store.c`) instead of the compile-time
`IDLE_TIMEOUT_MS` constant above — **`0` means disabled** (never
auto-sleeps from inactivity alone). **Default changed to `0`
(disabled)**, deliberately, for development — this codebase is being
actively exercised on hardware right now, and the device falling asleep
mid-session is friction, not the behavior being validated. A shipped
device should default back to the originally-validated 45 s; UI-SPECS.md
§2.13's SETTINGS_SECURITY "Auto-sleep after inactivity" field is the
(not yet built) screen that will let it be changed. Not yet
re-hardware-validated with this dev default.

**Amendment 2026-09-18 (settings engine refactor)**: `settings_store.c`
rewritten from hand-written per-setting NVS getter/setter pairs to a
table-driven engine — `settings_defs.inc` (X-macro: id, NVS key, type,
default, one line per setting) generates an internal id enum + lookup
table; two generic, mutex-protected functions (`settings_get_u32`/
`settings_set_u32`) do the actual NVS access, with the existing named
accessors (`settings_store_get/set_power_short_confirm`,
`..._idle_timeout_s`) becoming thin wrappers — public API unchanged, zero
changes needed in `ui_nav.cpp`/`main.c`. Prompted by a user question
comparing this to `references/Luc-Pibot-cnc-pendant-firmware`'s
`ESP3DSettings` module (`esp3d_settings.h`, X-macro-table + mutex +
schema versioning, doc: `docs/codewiki/settings.md` in that reference
tree) — that module's actual C++ class is too coupled to PiBot's own
WiFi/CNC/INI-update type system to import wholesale, but the table-driven
*pattern* was worth adopting now, cheaply, while there are only 2
settings to migrate, rather than after the duplication from hand-written
pairs gets worse (PIN, frontlight, owner info, and more are already
anticipated in `UI-SPECS.md`). The mutex closes a real, previously-latent
gap: multiple tasks (`ui_nav`, `power_button_task`, REPL commands) call
these accessors, and nothing serialized NVS access before this.
Schema versioning (also part of PiBot's module) was **not** adopted —
premature with 2 settings, revisit once there are enough to make a
breaking layout change plausible.

decision (2026-09-17) was to start with Settings specifically: it's the

The touch diagnostic screen ships UI-SPECS §2.12's "minimum useful"

**Amendment 2026-09-18 (continued) — touch responsiveness investigation**:
user reported touch as "barely reactive" (needing 5+ second holds to see
a value change in the touch diagnostic screen) and the fixed-zone
Settings/Back buttons never registering at all via touch, while
Left/Right/Power (plain GPIO, `buttons.c`) always work.

Two distinct findings:
1. **Real bug, fixed**: `touch.c`'s `touch_read()` ignored bits[3:0] of
   the GT911 status register (0x814E) — the datasheet-documented active
   touch-point count. It treated *any* "buffer ready" event (bit7 set) as
   a touch, including a release event (buffer ready, 0 points), parsing
   stale/garbage point data and reporting `pressed=true` for it. A real
   release edge was therefore only ever detected later, whenever a poll
   happened to see "no new buffer at all" instead of the chip's own
   release signal — a source of flaky/delayed release detection. Fixed by
   gating the point-register read (and `pressed=true`) on
   `touch_count > 0`; a 0-point buffer-ready event now correctly leaves
   `pt.pressed = false`. Also added an unconditional `ESP_LOGI` of the raw
   status byte + point count on every real chip activity sample (bounded
   rate — only fires while the chip actually has something to report), so
   the next hardware run's log shows exactly what the GT911 reports even
   for samples the caller's edge detection doesn't turn into an action —
   directly the "log the values" ask.
2. **Architectural, not yet fixed — needs a decision**: `board_ui_nav_task`
   is one single-threaded loop: read buttons -> read touch -> draw ->
   `eink_display_fb()`/`_fast()` (blocks the whole task for the flush
   duration, ~0.5-1s partial / ~2-4s full) -> loop. Both button and touch
   polling only happen once per loop iteration, so **any touch press or
   release that starts and ends entirely within a flush's blocking window
   is never sampled at all** — the loop resumes with the finger already
   up, sees no edge, and drops the tap silently. Physical buttons don't
   suffer this because they're level-based and the debounce
   (`buttons.c`'s `button_wait_press`) blocks on GPIO level, not a single
   instant sample: if a button is still held whenever the loop reaches it,
   it's caught, no matter how long the wait was. A quick tap is exactly
   the transient event this architecture is bad at. This plausibly
   explains both symptoms: needing to hold long enough to guarantee the
   press survives past whatever flush is in flight, and the Settings/Back
   buttons specifically feeling worse (each screen transition forces a
   full ~2-4s refresh via `s_force_full_refresh`, and a same-session
   Back tap right after opening Settings has to survive that whole
   window).

**Decision (2026-09-18)**: decouple input sampling from the render/flush
task rather than the smaller press/release mitigation — a real fix for
inputs dropped during a flush, not just a reduced-odds one.
Implemented:
- New `input_sampler_task` (`ui_nav.cpp`, its own FreeRTOS task, created
  from `board_ui_nav_task`) owns `button_wait_press()`/`touch_read()`
  exclusively now — the exact polling/edge-detection/settle-window logic
  that used to live inline in the render loop, unchanged in substance,
  just moved. It translates raw samples into discrete `InputEvent`s
  (`ButtonLeft`/`ButtonRight`/`ButtonPowerActivity`/`TouchPress`/
  `TouchRelease`) and posts them to a 16-deep `QueueHandle_t`
  (`s_input_queue`) — deep enough to buffer a realistic burst of taps
  across one flush.
- `board_ui_nav_task`'s render loop no longer touches hardware directly:
  it does `xQueueReceive(s_input_queue, &inev, pdMS_TO_TICKS(50))`
  (the 50ms timeout doubles as its existing idle-timeout polling tick),
  builds the same `InputSnapshot` it always did, and proceeds through
  the unchanged draw/flush pass. Since the sampler task is never blocked
  by the render task's `eink_display_fb()`/`_fast()` calls, a tap that
  happens mid-flush is now queued and processed on the very next loop
  iteration once the flush completes, instead of never being sampled at
  all. A backlog of several queued taps (e.g. from a long full-refresh
  transition) drains one event — and one full draw+flush cycle — per
  loop iteration, in order; no drops, at the cost of visibly "catching up"
  through a short train of redraws rather than losing the input.
- **REPL/serial input deliberately NOT folded into this queue**:
  `esp_console`'s REPL (`main.c`) already owns its own dedicated task
  with its own blocking serial read loop, was never coupled to
  `board_ui_nav_task`'s flush blocking to begin with, and already calls
  `board_activity_notify()` directly from its command handlers. Merging
  it in would mean reimplementing the REPL's read/parse loop ourselves
  for no actual gain.

### ADR-015: `docs/esp-project-boilerplate/` — extracting generic patterns

**Context**: several ADRs above (ADR-007 factory/recovery, ADR-008 board

**Decision**: a new `docs/esp-project-boilerplate/` directory, comparing

the project-specific tuning left out (PiBot's multi-board complexity, or

### ADR-016: Finalize device-level settings (idle timeout + frontlight)
before task 8.2

**Context**: ADR-014's closing summary named task 8.2 (`secret_store`
implementation) as the next step. The user requested reordering: finish
the device-level settings that have **no dependency on `secret_store`/
PIN** first — specifically the auto-sleep idle timeout (mechanism
already built and hardware-validated per ADR-012/013, but locked "off"
by a `MSF_DEBUG_NO_SLEEP` debug flag and only settable via REPL) and the
frontlight (LEDC pins hardware-validated per `hardware-specs.md`, but
zero software above the raw GPIO/PWM level — the Settings > Display row
was a hardcoded "not available yet" placeholder). Rationale: both are
self-contained, and finishing them now means the real product screens
(built after task 8.2) won't need the Settings menu's shape to change
again.

**Decisions (user-validated 2026-09-19)**:
1. Idle timeout: `MSF_DEBUG_NO_SLEEP` reverted to `0` (real sleep
   restored) now that the timeout is user-configurable — but the NVS
   default stays `0` (disabled), not reverted to ADR-012's originally-
   validated 45s. A `stepperRow` (±15s, range `[0,300]`, "Off" at 0) was
   added to the already-fully-enabled `SETTINGS_CONTROLS` screen, not a
   new half-built `SETTINGS_SECURITY` screen — that screen's other rows
   ("Change PIN", "Auto-lock (PIN)") still need `secret_store`. It will
   move into `SETTINGS_SECURITY` once that screen can ship as a whole.
2. Frontlight color is a **discrete Warm/Cool choice** (exactly one LEDC
   channel active at a time), not a continuous warm↔cool blend like
   `freeink-sdk`'s `FrontlightManager` — matches `UI-SPECS.md` §2.14's
   ASCII mockup exactly and needs no blending math.
3. New `boards/x4pro/app/frontlight.h`/`.c`: a small native ESP-IDF LEDC
   driver (one timer, 25 kHz/10-bit, two channels — cool `GPIO8`/warm
   `GPIO9`, `hw_config.h`), pattern-matched to
   `references/Luc-Pibot-cnc-pendant-firmware`'s `disp_backlight.c`
   (single-channel LEDC driver, extended to 2 channels) rather than
   porting `freeink-sdk`'s `FrontlightManager` C++ class (gamma curve +
   blending + deep-sleep park/release — more than this design needs, per
   [[feedback_check_pibot_reference]]'s "extract the pattern, don't
   vendor the class" precedent already used in ADR-010).
4. Four new NVS settings (`settings_defs.inc`): `FrontlightOn`,
   `FrontlightColor`, `FrontlightIntensity` (0-100), `FrontlightAutoOffS`
   — same X-macro pattern as `PowerShortConfirm`/`IdleTimeoutS`
   (ADR-012's amendment). New `Screen::SettingsDisplay` in `ui_nav.cpp`:
   a `toggleRow` (on/off), a `settingRow` with a cycling value (color —
   reuses the existing tappable-row widget instead of building a new
   segmented-control component), a `sliderRow` (intensity, buttons-only,
   no drag wired), and a `stepperRow` (auto-off). Every change applies
   immediately via `frontlight_apply()`, mirroring
   `ACTION_TOGGLE_POWER_CONFIRM`'s no-cached-state pattern.
5. **Auto-off design choice**: cuts the physical LEDC output only after
   inactivity — it does NOT clear the persisted "on" NVS preference, so
   the light does not relight itself on the next touch (mirrors the
   existing idle-sleep mechanism, which also never auto-wakes). The user
   re-toggles it explicitly.
6. `splash.cpp`'s `board_sleep_screen_show()` now also calls
   `frontlight_off()` alongside the existing `rails_hold_for_sleep()`,
   guaranteeing the light is off before deep sleep regardless of whether
   auto-off already fired. No `rtc_gpio_hold_en()` added for the two
   frontlight pins (unlike the touch/SD rails): their "off" level is
   duty-0/LOW, the same state an un-driven pad defaults to, not an
   active-HIGH level that must be actively held through sleep — flagged
   as a hardware-validation follow-up (watch for flicker/drain) rather
   than built preemptively.

**Status**: build-verified only (`./msf_build.bat build`, clean) as of
2026-09-19. Hardware validation (idle-sleep actually firing again at a
configured timeout, frontlight on/off/color/intensity/auto-off, light

**Amendment 2026-09-20 (first hardware round) — 6 fixes from real usage**:

**Refactor**: `ui_nav.cpp` (1226 lines: all 6 screens + every shared
widget builder in one file) split into `ui_screens.h` (the internal
Screen enum + `switch_screen()`/`build_xxx()` contract shared between
files), `ui_widgets.h/.cpp` (generic builders: buttons, rows, toggles,

**Fixes, all found via hardware testing with added timestamped logging**
(touch press/release in `lv_port_indev.c`, value changes in
`ui_screen_settings_display.cpp`, flush duration in `lv_port_disp.c`):
1. Left/Right focus moves no longer force a full e-ink GC refresh (a fast
   DU redraw is enough for a focus outline) — was making every navigation
   step take a full ~1.5s GC for no visual reason.
2. `touch.c`'s I2C device handle is now cached in `touch_init()` instead
   of opened/closed on every single register access (was happening 2-3x
   per ~20ms poll) — cut touch-sampling latency and heap churn.
3. `eink.c`'s mandatory ghost-budget full refresh (~30 fast DUs since the
   last full one) is now slipped into an idle gap between interactions
   (`ui_nav.cpp`'s `maybe_run_ghost_housekeeping()`, backed by a new
   `eink_ghost_budget_low()` query) instead of landing at random on
   whatever flush the user happens to be waiting on for their last tap —
   root cause of a reported "+ button takes 4-6s to show 100%".
4. Real dropped-click bug in `touch.c`: a held touch could intermittently
   report `x=-1,y=-1` on a poll where the GT911 had no fresh buffer yet
   (chip doesn't re-assert "buffer ready" every single ~20ms poll while a
   finger is stationary) — LVGL re-hit-tests the touched object on every
   `PRESSED` sample, so a stray `(-1,-1)` fired `PRESS_LOST` on the real
   button and the eventual release found no active object left: focus
   stayed visible (set before the glitch) but `CLICKED` never fired.
   Fixed by holding the last known-good coordinate across those gaps
   (`lv_port_indev.c`'s `input_sampler_task`).
5. Replaced the level-based touch state fed to LVGL's pointer indev with
   a discrete press/release edge queue (`lv_port_indev.c`, 16 deep),
   drained via LVGL's own `continue_reading` mechanism. A tap whose whole
   press+release cycle happened to fall inside a slow flush's blocking
   window used to be entirely invisible to LVGL (this app's single task
   both flushes and pumps `lv_timer_handler()`); queued edges are now
   always replayed in order once the task frees up, however late.
6. New `ui_defer()` (`ui_widgets.h`, thin `lv_async_call()` wrapper),
   used by **every** click/value-changed callback across every screen, no
   per-control judgment calls. Root incident: Settings > Display's
   Frontlight toggle mutates its own `lv_group_t`'s membership
   (`lv_group_add_obj()`/`lv_group_remove_obj()`, showing/hiding the
   Color/Intensity rows) from directly inside the event callback that
   same group's click triggered — confirmed on hardware to occasionally
   drop a rapid second tap's effect entirely. No other control happened
   to mutate group/object structure from its own handler, so nothing else
   had hit this yet, but the next one to would have, with nothing in the
   code hinting at the risk. Deferring universally removes the whole
   hazard class instead of relying on each future control's author to
   recognize it (cost: ~1 `lv_timer_handler()` pass of latency, <20ms,
   negligible against this panel's 700-1500ms flush times). The one
   documented exception is `toggle_confirm_click_cb()`, which needs
   `lv_indev_get_act()` read synchronously to tell a real tap from the
   Power/touch-Home confirm pulse.
7. `board_ui_nav_focus_prev/next()`/`board_ui_nav_power_confirm()`
   (`ui_nav.cpp`/`ui_nav.h`) changed from `std::atomic<bool>` flags to
   `std::atomic<int>` counters, and `board_ui_nav_task`'s loop now drains
   all pending steps, not just one — same coalescing risk as #5 above,
   at the physical-button level: two quick presses of the same button
   landing while the loop is busy used to collapse into a single action.

**Verified on hardware**: dozens of rapid taps on Intensity/Color/
Frontlight, including back-to-back double-taps that previously
reproduced fix #6's drop, all registering correctly; a full `idf.py
build` after all of the above compiles clean.

**Amendment 2026-09-23 — zone refresh + the two remaining minor fixes**.

**Zone refresh**: turns out LVGL already computes the exact invalidated
rectangle and hands it to `flush_cb()` as its `area` parameter -- even
under `LV_DISPLAY_RENDER_MODE_FULL` (`lv_refr.c`'s `refr_invalid_areas()`/
`disp->refreshed_area`; the render *buffer* covers the whole screen in
this mode, but the *changed region* is tracked separately). No manual
pixel diffing needed: `flush_cb()` was simply discarding an `area` LVGL
already gave it for free. New `eink_display_fb_fast_region(fb, y_start,
y_end)` (`eink.c`/`.h`) restricts the `PTL` command's gate/row window to
the given range instead of the full 480 gates -- the SPI transfer still
streams the complete frame (`stream_plane()` has no partial-row write
path, left untouched/validated), only which rows the *controller*
actually rescans on the physical panel is restricted, which is the
dimension that costs refresh time (sequential gate scan). `flush_cb()`
(`lv_port_disp.c`) now transposes `area`'s portrait ux-range through the
existing portrait->native mapping (`fb_y = SCREEN_WIDTH-1-ux`) into that
gate window. Forced full GC refreshes stay deliberately unrestricted
(their whole purpose is purging ghosting everywhere). Hardware-validated:
browsed every screen, no regressions.

**`lv_port_disp_init()`**: now `abort()`s with a clear log line if the
PSRAM frame-buffer allocation fails, instead of silently leaving LVGL
unconfigured and crashing confusingly later in `build_screens()`.

**`buttons.c`**: `button_wait_press()` (blocked on the physical level
until release) replaced by `buttons_read_raw()` (instantaneous, never
blocks). Debounce + edge detection moved into `lv_port_indev.c`'s
`input_sampler_task`, interleaved with touch sampling every iteration
(same pattern already used there for touch) and still firing on the
RELEASE edge to match the old behavior -- holding Left/Right no longer
stalls touch sampling in the same loop.

**Amendment 2026-09-24 — Touch Calibration screen rebuilt, and the touch
Y mapping itself fixed**. Hardware-validated: 8px residual error after the
guided run, Back reachable by touch immediately after, calibration
persisted across a reboot, header buttons (y~92-109) now reachable.

*Screen* (`ui_screen_touch_diag.cpp`): the old one (5 crosses + tick column
+ live readout, all absolutely positioned, overlapping the header) was a
one-off diagnostic, not a calibration. Now a guided 9-target sequence, one
crosshair at a time, 3 taps averaged per target with an explicit "1✓ 2✓ 3"
counter; on completion `touch_calibrate()` (`touch.c`) least-squares fits a
per-unit scale+offset per axis, applies it, persists it to NVS (4 new
`tc_*` settings) and **reads it back to verify** before claiming "saved".
A fit outside sane bounds (`calibration_fit_is_sane()`: scale 0.5x-2x,
offset within the panel) is rejected outright — an unsafe fit once made
every tap read Y=0. Each run saves the previous correction first and
restores it on any failure. Result shown as SUCCESS/FAILED for 3s, then the
detail. Restart sits in the header (mirrors Back).

*Escape hatch*: while a run is in progress, Back/Restart only respond to the
physical buttons (Left/Right + Power) — direct touch on them and the
touch-Home confirm pulse are ignored (`board_ui_nav_suppress_touch_confirm()`,
`board_ui_nav_power_confirm(from_touch_home)` now carries its origin). The
restriction lifts as soon as the outcome is known, so tapping Back doubles
as an immediate touch check. 30s without progress leaves the screen. The
battery label timer is suspended on this screen.

*Tap counting robustness*: a tap is only counted once at least one flush has
completed since the target moved (`lv_port_disp_get_flush_count()`) — a
fixed delay guess was tried first and let stale taps through (e-ink takes
0.7-1.5s to show the new target); plus a 400ms anti-bounce.

*Root causes found by mapping sweeps* (screen temporarily repurposed;
the `TOUCH_CAL_MAPPING_MODE` scaffold was removed once done -- see git history to re-run one): `touch_lerp_y()` was a 2-segment
fit (2026-09-18) that (a) hid a **plateau + cliff** — raw_x nearly flat for
y=440-490 (~322→315) then dropping ~180 units by y=500 — which no linear
correction can represent (fits came out 3x out of bounds), and (b) clamped
every raw_x >= 415 to y=240, so **no tap above y~240 could land on the
header buttons**. Replaced by a 14-breakpoint piecewise table
(`kTouchYBreakpoints`, y=90..750) from dense single-tap sweeps. Likely
underlying cause: this unit runs a generic substitute GT911 config (own OTP
blank, `docs/touch-calibration-notes.md` §2), not X4 Pro's real one. The
top ~87px is a touch dead zone (§10), so nothing registers above it.

*Also*: calibration grid rows moved to y=200/460/720 — a grid covering only
y=520-700 made the global linear fit extrapolate to the header (a Back tap
came out ~50px low and hit "Controls"). Home-zone aliasing near the
bottom-right corner (`home=1`) also avoided by keeping targets off it. The
battery label now only updates when its text changes; the ghost-budget
idle housekeeping refresh was removed (any refresh without a direct
interaction is unwanted; the hard 30-DU budget in `eink.c` is unchanged).

## Project rules

1. **No code without a spec** — Every component has a documented header before implementation.
