> **Version**: 1.0  
> **Date**: 2026-08-30  
> **Status**: Phase 2 — To be validated

---

## 1. Objective

Set up a **reference service** with TOTP 2FA enabled, serving as ground truth to validate:
- The Python implementation (`totp_reference.py`)
- The C/ESP-IDF implementation (`test_totp/`)
- The final firmware on X4 Pro

The service must be **disposable**: if our TOTP implementation fails and locks us out, we can recreate it in a few minutes without losing any personal data.

---

## 2. Target service: GitHub (dedicated account)

### Why GitHub?

| Criterion | GitHub |
|---------|--------|
| Free | ✅ Free tier |
| Native TOTP 2FA | ✅ Authenticator app (TOTP) |
| Backup codes | ✅ 16 codes can be generated |
| Easy to reset | ✅ 2FA can be disabled via backup email |
| No sensitive data | ✅ Dedicated, disposable account |
| Auth logs | ✅ Login history visible |
| API / CLI | ✅ `gh auth` for automated tests |

### Why NOT a personal Google account?

- A Google account is too critical. If our TOTP fails and we don't have the backup codes, it's a disaster.
- A dedicated GitHub account carries zero emotional stakes.

## 3. Test account creation procedure

### 3.1 Account creation

1. Go to https://github.com/signup
2. Create an account with:
   - Email: a disposable address (e.g. `x4pro-test@yopmail.com` or an alias)
   - Username: `x4pro-totp-test` (or similar)
   - Password: generated by a password manager
3. **Do NOT link a phone number** (we want pure TOTP, not SMS)

### 3.2 Enabling TOTP 2FA

1. Settings → Password and authentication → Two-factor authentication
2. Click "Enable two-factor authentication"
3. Choose **"Authenticator app"** (not SMS, not a security key)
4. GitHub displays a **QR code** and a **secret key in text form** (Base32 format)
5. **Capture the Base32 secret key** — this is the shared secret for our TOTP
6. Complete activation with the first generated code

### 3.3 Saving the recovery codes

GitHub generates **16 single-use recovery codes**.

1. **Save them immediately** in an encrypted file or on paper
2. Name the file `github-recovery-codes.txt`
3. These codes are used to regain access if our TOTP doesn't work

### 3.4 Saving the TOTP secret

The Base32 secret shown by GitHub during activation is the key.

1. Copy the secret into a file `github-totp-secret.txt`
2. This file will be read by `totp_reference.py --secret-file`
3. **NEVER commit this file** — add it to `.gitignore`

## 4. Recovery procedure (in case of lockout)

### Scenario 1: Our TOTP doesn't work, but we have the recovery codes

1. Go to https://github.com/login
2. Enter email + password
3. When asked for the 2FA code, click "Use a recovery code"
4. Enter one of the 16 recovery codes
5. Access restored → temporarily disable 2FA → restart the tests

### Scenario 2: We lost the recovery codes (disaster)

1. GitHub allows recovery via a verified email
2. Recovery delay: 24-72h
3. **Mitigation**: keep the recovery codes in 2 separate physical locations

### Scenario 3: We want to start over from scratch

1. Log into the account (with a recovery code if needed)
2. Settings → Password and authentication → Disable 2FA
3. Delete the account if it's truly disposable: Settings → Account → Delete account
4. Recreate a new GitHub account in 5 minutes

## 5. Validation strategy

### 5.1 Python validation (Phase 3)

**Tool**: `totp_reference.py --secret-file github-totp-secret.txt`

| Test # | Description | Success criteria |
|--------|-------------|-------------------|
| T1 | Current code matches GitHub login | 1 valid code out of 1 attempt |
| T2 | 5 consecutive codes match | 5/5 codes validated over 2.5 min |
| T3 | Drift tolerance | Codes valid within ±1 window (±30s) accepted |
| T4 | Transition window | Previous code accepted 5s after expiration |
| T5 | C array export | Array copy-pasted without error |
| T6 | Secret re-entered | Identical result with secret retyped by hand |

**Exit gate**: T1-T6 all pass.

### 5.2 ESP-IDF C validation (Phase 4)

**Tool**: `test_totp/` flashed onto a generic ESP32

| Test # | Description | Success criteria |
|--------|-------------|-------------------|
| E1 | RFC 6238 self-test at boot | 6/6 vectors pass |
| E2 | Current code matches GitHub | 1 valid code out of 1 attempt |
| E3 | 5 consecutive codes match | 5/5 codes validated over 2.5 min |
| E4 | Identical to Python | ESP32 code == Python code for the same timestamp |
| E5 | 24h stability | Device powered on for 24h, codes still correct |

**Exit gate**: E1-E5 all pass.

### 5.3 X4 Pro validation (Phase 8)

| Test # | Description | Success criteria |
|--------|-------------|-------------------|
| X1 | Code displayed on E-Ink matches GitHub | 1 valid code |
| X2 | Accurate visual timer | Progress bar in sync with actual expiration |
| X3 | Service list navigation | Selecting a service → correct code |
| X4 | Deep sleep recovery | After 1h of deep sleep, code still correct |

## 6. Detailed test scenarios

### Test T1: Immediate match

```bash
# Generate the code
python totp_reference.py --secret-file github-totp-secret.txt

# Open https://github.com/login in a private browser window
# Enter credentials
# When asked for the 2FA code, enter the code shown by the script
# Expected result: successful login
```

### Test T2: Code sequence

```bash
# Watch mode for 3 minutes
python totp_reference.py --secret-file github-totp-secret.txt --watch

# Attempt to log into GitHub at t=0s, t=30s, t=60s, t=90s, t=120s
# Expected result: 5 successful logins out of 5
```

### Test T3: Drift

```bash
# If a code doesn't work:
python totp_reference.py --secret-file github-totp-secret.txt --drift

# Enter the code shown by GitHub/Authy
# The script computes the offset
# Expected result: drift < 30s (if > 30s, secret or clock issue)
```

### Test T4: Window transition

```bash
# Generate a code at t=28s (2s before expiration)
# Attempt login at t=28s → should work
# Wait until t=32s (2s after expiration)
# Attempt login with the NEW code → should work
# Attempt login with the OLD code → should fail
```
